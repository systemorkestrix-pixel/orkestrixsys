# Orkestrix Systems — خطة إغلاق الموقع

هذه خطة تنفيذ لاحقة مبنية على [تدقيق النظام](../audits/system-audit.md). لا تعني أن أي مرحلة مصرح بها تلقائيًا؛ خصوصًا المراحل التي تحتاج قرارًا تجاريًا أو قناة بيانات خارجية.

## قواعد لا تتغير

- العلامة: **Orkestrix Systems**.
- التموضع: **Digital Systems for Businesses**.
- الوعد: **من الفكرة إلى التشغيل.**
- الخدمات: خمس فئات فقط، وبالترتيب المعتمد.
- مسار التسليم: فكرة → تخطيط → تصميم → تطوير → قاعدة بيانات → لوحة إدارة → ربط الخدمات → دومين → استضافة → SSL → نشر → تشغيل ودعم.
- لا تبنَ Project Details أو Dashboard قبل إغلاق Projects وContact.

## Phase A — Homepage Closure

### المنجز

- رسالة العلامة، رحلة العمل، الخدمات المختصرة، FAQ، وروابط الاستكشاف موجودة.
- روابط بطاقات الخدمات تقود إلى تفاصيل الخدمة المطابقة.

### المتبقي

- اعتماد سياسة CTA النهائية: مباشر إلى الطلب أو استكشافي حتى نهاية المسار.
- إصلاح metadata الأساسية للصفحة الرئيسية وإجراء اختبار هاتف يدوي.

### المحظور تغييره

- لا تتحول الرئيسية إلى catalogue تقني أو Portfolio.
- لا تعاد كتابة مراحل التسليم المعتمدة.

### معايير القبول

- يفهم زائر جديد من أنتم، ماذا تبنون، كيف تعملون، وإلى أين ينتقل بعد ذلك.
- metadata العربية سليمة وcanonical/OG قابلان للتحقق.
- Hero والقائمة والـFAQ والبطاقات تعمل على 320/375/430/768/1440px.

## Phase B — Services Closure

### المنجز

- الخدمات الخمس الرسمية موجودة مع وصف وتفاصيل ومسار اختيار وتسليم.
- Hero ثانوي كامل العرض ومختلف بصريًا عن الرئيسية.

### المتبقي

- اعتماد CTA الرسمي المتسق مع Phase A.
- مراجعة تكرار الرسائل حول «من الفكرة إلى التشغيل» بعد قرار CTA.
- اختبار التكوين البصري للـHero على الهاتف.

### المحظور تغييره

- لا تضاف فئات خدمات جديدة.
- لا تتحول الصفحة إلى أسعار أو قائمة تقنيات أو تكرار للصفحة الرئيسية.

### معايير القبول

- يحدد الزائر نوع احتياجه أو يعرف أين يطلب المساعدة في تحديده.
- كل خدمة تشرح المشكلة والحل والقيمة دون ادعاء غير مدعوم.
- الانتقال إلى Projects واضح ومقصود.

## Phase C — Projects Closure

### المنجز

- يوجد مسار `/projects` وروابط إليه، وتوجد قواعد تصميمية مبدئية غير موصولة بمكوّن فعلي.

### المتبقي

- إنشاء مصدر بيانات مشاريع يميز بوضوح بين مشروع حقيقي، نموذج مفاهيمي، وتجربة داخلية.
- بناء hierarchy: featured project، project cards، حالة/فئة، رابط Preview إلى slug.
- تحديد ما يُعرض كدليل: المشكلة، الحل، نطاق التنفيذ، والنتيجة المتاحة فقط.
- ربط كل بطاقة بمسار `/projects/[slug]` مستقبلي دون بناء صفحة التفاصيل في هذه المرحلة.

### العوائق

- لا توجد حاليًا بيانات مشاريع أو أدلة نتائج أو سياسة تصنيف demo/real.

### المحظور تغييره

- لا تتحول الصفحة إلى gallery صور أو ادعاءات نتائج غير موثقة.
- لا تبدأ Project Details قبل نجاح معايير هذه المرحلة.

### معايير القبول

- `/projects` يؤدي دور Proof بوضوح.
- كل بطاقة تملك هوية/slug وحالة معلنة.
- لا توجد بطاقة بلا سياق أو رابط بلا وجهة مخططة.

## Phase D — About Closure

### المنجز

- المبادئ والمنهج موجودان جزئيًا في الصفحة الرئيسية.

### المتبقي

- قرار صريح: تنفيذ `/about` أو تأجيله وإبقاؤه خارج التنقل حتى ذلك الحين.

### العوائق

- لا يوجد محتوى معتمد خاص بالثقافة أو الفريق أو مبدأ العمل خارج ما في الرئيسية.

### المحظور تغييره

- لا تكرر الرئيسية ولا تبنِ سيرة ذاتية طويلة.

### معايير القبول

- إن نُفذت، تشرح المبدأ والثقافة والمنهج بإيجاز.
- إن أُجلت، لا يظهر لها رابط أو وعد في التنقل أو sitemap.

## Phase E — Contact / Project Request Closure

### المنجز

- يوجد نموذج يجمع الاسم، النشاط، قناة التواصل، والفكرة.
- توجد صفحة نجاح شكلية فقط.

### المتبقي

- اختيار وجهة الاستلام: بريد/CRM/API/قاعدة بيانات، ومن يملك الوصول إليها.
- validation خادمي، معالجة خطأ، حماية spam، حفظ request ID، وإشعار داخلي.
- تأهيل بسيط يطابق الخدمة المطلوبة بدون تحويله إلى استبيان طويل.
- كتابة نجاح صادق لا يظهر قبل تأكيد الاستلام.

### العوائق

- يلزم قرار المستخدم حول مزود البيانات أو البريد أو CRM؛ لا يمكن افتراضه.

### المحظور تغييره

- لا يقال «وصلتنا الفكرة» قبل وجود تسليم ناجح قابل للتحقق.
- لا تحول الصفحة إلى نموذج Contact عام.

### معايير القبول

- كل إرسال ينتج طلبًا محفوظًا وقابلًا للتتبع أو إخطارًا مؤكدًا.
- رسالة الخطأ والاستلام حقيقية ويمكن اختبارها.
- بيانات الزائر تعامل بسياسة خصوصية مناسبة.

## Phase F — Project Details

### المنجز

- توجد فقط قواعد CSS استباقية؛ لا يوجد route أو data model أو مكوّن تفصيلي فعلي.

### المتبقي

- route `/projects/[slug]`، 404، وبيانات تفصيلية لكل مشروع.
- قصة ثابتة: المشكلة → السياق → الحل → التنفيذ → النتيجة/حدود النتيجة → CTA.

### العوائق

- تتطلب Projects مغلقة وslugs ومحتوى حالات معتمد.

### المحظور تغييره

- لا تستخدم نتائج رقمية أو شهادات لا يمكن إثباتها.

### معايير القبول

- كل slug من Projects يفتح قصة صحيحة، والمسار غير المعروف يظهر 404.

## Phase G — Database + Dashboard

### المنجز

- لا توجد طبقة بيانات تشغيلية في النسخة الحالية.

### المتبقي

- نموذج بيانات للطلبات والمشاريع، مصادقة، صلاحيات، سجل نشاط، ولوحة إدارة بالحد الأدنى الضروري.

### العوائق

- لا يبدأ قبل إغلاق Contact وتحديد lifecycle للطلب.

### المحظور تغييره

- لا تبنِ Dashboard قبل وجود مستخدمين وأدوار وعمليات محددة.

### معايير القبول

- يمكن للفريق رؤية الطلبات، تحديث حالتها، ومتابعة مصدرها بأمان.

## Phase H — Deployment + Launch

### المنجز

- build وtypecheck ينجحان محليًا، و`robots.txt` وfavicon موجودان.

### المتبقي

- fallback لمسارات SPA، sitemap، canonical/OG كامل، analytics/consent بحسب القرار، مراقبة الأخطاء، وفحص الروابط الخارجية والداخلية.
- اختبار وصول وهاتف ومتصفحات وإرسال طلب حقيقي في البيئة المنشورة.

### العوائق

- يحتاج نطاق النشر وخيارات الاستضافة وقناة الطلب النهائية.

### المحظور تغييره

- لا تغيّر إعدادات النشر أو DNS دون تفويض صريح.

### معايير القبول

- كل المسارات العامة تعمل مباشرة بعد refresh.
- metadata قابلة للفحص، ولا توجد روابط مكسورة أو رسالة نجاح كاذبة.
- طلب اختبار يصل إلى وجهته وينشأ تنبيهًا صحيحًا.

## بوابة القرار التالية

نحن بعد المراجعة في مرحلة: **إغلاق الصفحة الرئيسية والخدمات بشروط، ثم إغلاق Projects**.

العمل التالي بالترتيب:

1. اعتماد سياسة CTA.
2. إغلاق Projects ببيانات ومحتوى Preview حقيقيين.
3. تحديد وجهة استقبال Project Request.
4. إغلاق Contact فعليًا.
5. عندها فقط بناء Project Details ثم البيانات ولوحة الإدارة.

لا يُبنى قبل إغلاق ما قبله: Project Details، Database، Dashboard، Notifications، أو نشر نهائي.
